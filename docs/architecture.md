# Архитектура Keepr

## Границы

`keepr-core`: модель, валидация, календарная арифметика, транзакции, история, здоровье, очередь уведомлений. Не зависит от Tauri/GTK. Время передаётся в операции явно, поэтому тестам не нужно менять часы ОС.

`src-tauri`: ограниченные IPC-команды, actor базы, жизненный цикл окон, native notifications, tray, автозапуск. Один выделенный поток владеет SQLite; ограниченный канал сериализует операции. Ошибки возвращают UI стабильные коды, технические детали попадают в локальный лог.

`src`: Svelte presentation, формы, доступные диалоги, SVG. После commit Rust отправляет сигнал `changed`; UI перечитывает snapshot. Счётчик запросов предотвращает применение устаревшего ответа. При фокусе данные сверяются снова.

## Хранение и изменения

SQLite: WAL, `foreign_keys=ON`, `synchronous=FULL`, `busy_timeout`. Начальная SQL-миграция атомарна, `user_version` проверяется при старте. Более новая неизвестная схема не открывается для записи. Последующие изменения требуют новой миграции и теста обновления существующей БД.

У предмета есть UUID текущего цикла и revision. Выполнение требует ожидаемую revision. Завершённый цикл, новое состояние предмета и запись журнала фиксируются одной транзакцией. Повторный или устаревший запрос получает `conflict` и не завершает следующий цикл.

Отмена хранит снимок предыдущего предмета и ожидаемую результирующую revision. После другого изменения отмена отклоняется. Событие помечается отменённым; история сохраняется. Удаление предмета мягкое. Удаление комнаты сохраняет вещи без комнаты.

Версия схемы 2 добавляет удаление отдельных записей журнала. `events.deleted_token` исключает запись из общего журнала и истории предмета, но сохраняет факт действия для расчёта здоровья, уровня и отмены действий над предметом. Каждому удалению выдаётся новый токен: старое действие «Вернуть» не восстанавливает более позднее удаление. Удаление/восстановление сообщения не создаёт дополнительных записей в журнале. При обновлении существующей БД автоматически сохраняется `keepr.before-v2.keepr`; поддерживается импорт резервных копий схем 1 и 2.

Экспорт использует SQLite Online Backup API, поэтому учитывает WAL. При восстановлении исходная БД открывается read-only, проверяются целостность, версия и доменные поля. В нашу схему импортируются данные, не чужие SQL-триггеры. Замена атомарна. Перед ней сохраняется `before-restore.keepr`.

## Даты

Сроки — civil dates (`YYYY-MM-DD`). Моменты событий и отложенных уведомлений — RFC3339 UTC. Дом имеет фиксированный IANA timezone; смена системной зоны во время поездки не переносит домашние сроки. Изменение зоны в настройках перепланирует напоминания.

Повторения считаются от даты фактического выполнения. Календарный месяц не равен 30 дням; несуществующее число зажимается до конца месяца. После 29 февраля + год получается 28 февраля. Разовое выполнение закрывает предмет; он может начать новый цикл с выбранной датой.

«Через час» — 3600 секунд. «Завтра» — следующий день в установленное время напоминаний. «До вечера» — ближайшие будущие 19:00. Snooze меняет время напоминания, не срок вещи. В DST-fold выбирается первый момент, в DST-gap — первая существующая минута после разрыва.

## Напоминания и фон

Один resident-процесс запускается при входе пользователя. В Tauri configuration нет автоматически создаваемых окон. Закрытие окна уничтожает WebView; `ExitRequested` удерживает Rust-процесс до явного выхода из трея. Новое окно создаётся на отдельном потоке, что избегает известной Windows WebView2 deadlock-ситуации.

Планировщик спит до ближайшего напоминания/полуночи или изменения данных. Каждые 60 секунд проверяются только часы, без запроса БД. Linux дополнительно слушает `PrepareForSleep` на D-Bus. Пробуждение и скачок времени вызывают пересчёт. Отсутствие logind допускается.

Идентичность доставки: UUID цикла + срок + календарный день. Косметические изменения не создают повторных уведомлений. Отложенное напоминание имеет отдельный ключ. Неуспешная доставка повторяется через 5 минут. В обычном режиме — не более одного напоминания на предмет за день; несколько накопившихся событий объединяются.

Квитанция и внешняя ОС не могут быть записаны одной транзакцией: при аварии между отправкой и записью возможно повторное уведомление. Бизнес-действия при этом защищены revision-проверкой. Уведомления — подсказка; SQLite остаётся источником истины.

Отправка выполняется через `notify-rust` на блокирующем потоке. Результат системного транспорта ожидается до записи квитанции. Это также обходит обнаруженное при E2E поведение Tauri notification-плагина: detached task теряет ошибку доставки и вызывает nested-runtime panic с текущей Linux D-Bus-конфигурацией.

## Визуальная система

CSS semantic tokens: поверхности, текст, границы, основной цвет, срочность; отдельные палитры тем. Нежная игровая составляющая: авторские SVG-вещи, кольца, хранитель, 10 забот на уровень. Алгоритм здоровья сглаживает маленькие дома и учитывает длительность просрочек. Текст дублирует цвет состояния.

Native `<dialog>` удерживает фокус и поддерживает Escape; фокус возвращается к инициатору. `prefers-reduced-motion` отключает анимации. Ctrl+N добавляет вещь, Ctrl+K открывает поиск.
